What it is

一个能被 AI 直接执行的设计系统 - 把「设计系统&设计技能&协作原则」转译成 AI 能读懂的语言，让它替你画符合得物规范的界面——而不是"看起来差不多"的草稿。

14 条协作原则3 个 Skill8 类 design token 29 个组件 7 种布局

它靠什么保证质量

Quality control

三层防线，「生成前」建立标尺 → 「生成中」精准路由 → 「生成后」校验盖章。

1

设计规范为基准

design token / 组件 / 布局 是唯一依据。色值、字号、间距必须能指到出处，禁止 AI 自行发明；文档没写明的，它停下来问，而不是瞎编。

2

生成前组件映射

画之前先把每个 UI 元素列一遍 → 逐个查有没有对应组件 → 有就用组件、没有才标兜底。从源头堵住"随手用浏览器原生组件"这类偷懒。

3

生成后强制自检

共计有 13 项自检原则。下面这些是命中即判 FAIL 的硬性触发器：

1 视觉属性有出处2 不用浏览原生控件3 图标正确引用4 不自绘节点5 间距走 token6 遵循对齐原则7 文本不溢出8 位置检验9 布局符合场景规范10 商品用真实资料11 覆盖需求文档12 信息架构合理
元素实际实现组件映射判定
日期选择<input type=date>无——原生控件FAIL · F1
标题序号.section-index 自绘圆点无对应组件FAIL · F4

编排层（Workflow）

编排主流程：需求理解 → 生成页面。定义每一步由谁执行、什么时候停下来等等人。它是"开工须知"，唤醒任务对应的skill。

principles /

约束层（Principles）

全局协作原则：规定 AI 什么不许做、又必须做什么，要求交付前强制自检。先立规矩，再动手。

设计 Skills

独立可调用的原子能力：解析需求、匹配规范、自检、导出 Figma 等。由 Workflow 按需调用，单一职责。

Design.md · 设计规范

3 Skills

组件文档生成

component.skill

从 Figma 规范页反推出得物设计系统的组件 Markdown，逐个登记进组件树状图。相当于给设计系统建一本 AI 能查的"字典"。入库动作：设计系统从这里长大。

商家端 UI 生成

page_builder.skill

生成页面：大量翻 token.md 找色值、翻 button.md 找状态、翻 scenario.md 找编排规则。用已有的规则，搭出符合得物设计规范的页面。消费动作：把规范用出去。

设计规范校验

checker.skill

比对「规范说的」和「实际做的」，揪出不一致，输出差异报告——哪个色值不在 token 表，并附修复建议。守门动作，防止规范和实现漂移。

34 Design.md

Design Token

8 类 design token：色彩 / 字体 / 间距 / 尺寸 / 圆角 等，附命名与语义规则，是所有取值的唯一来源。

原子组件

26 个商家端组件资产：Button / Input / Select / DatePicker 等，每个含变体规格、使用场景、树状决策图。

业务布局

7 个页面布局模版 + 业务组件（搜索 / 筛选表单、编辑 / 详情表单），把常见页面结构固化成模板。

Assets

商品预填

50 条真实商品 SPU（真实商品名 / 图），禁止"示例商品 1"这类占位，出图即接近真实。

素材库

Workflow

02生成结构化需求文档
03一句 prompt 交给它画

Step 1用 PRD 生成「AI 可用的需求文档」

先别急着画：把 PRD + 原型喂给 AI，让它产出一份结构化需求文档——把要素按「能不能改」分成 [硬] 不可改 / [参考] 可优化 / [待拍板] 需先定 三档。

需求文档生成 · prompt 骨架
角色 & 目标

资深产品需求分析：把 PRD + 原型 整理成一份「设计可直接消费的需求文档 .md」，严格按方法执行，最终只输出一个 .md。

我的输入 · 5 项

① PRD　② 原型（Figma 带 node-id / 截图）　③ 竞品参考（可选）　④ 本次范围（只做一条路径）　⑤ 设计系统文档（可选）

执行步骤 · A–H

A 通读 PRD　B 逐屏拆原型（字段穷举 / 联动变体 / 状态机 / 空态）　C 范围纪律　D 三色标注 [硬]/[参考]/[待拍板]　E PRD ↔ 原型交叉核对（冲突/缺失/多出 → 全列 [待拍板]）　F 术语与指标口径对齐　G 竞品只借方法论　H 组件清单与缺口（只到通用类型）

硬规则

只用真实信息 · 字段穷举不含糊 · 结构性决策先停下标 [待拍板] · 不虚构设计系统数值 · 组件不写死（componentKey / 变体留给设计系统绑）· 只交付一个 .md。

输出结构 · 0–8

0 使用边界 · 1 路径概述 · 2 信息架构 · 3 页面清单 · 4 逐页详述 · 5 术语指标对齐 · 6 竞品借鉴 · 7 待拍板汇总 · 8 组件清单与缺口 · 附 原型节点索引

📌 完整 prompt 略——此处只展示骨架：用固定结构约束 AI，从源头保证产出的需求文档结构化、可被设计直接消费。

Step 2把需求文档交给它画，你来判断

一句 prompt 交给它。需求里标了 [待拍板] 的结构性决策，AI 不自作主张——先列出来让你选，你定了再画。这就是「文档没提清楚的地方，它停下来问」。

Step 3一轮：生成页面 & 自检

AI 出静态 + 交互两版页面，边生成边自检——比如自己发现某个联动变体横向溢出、配额表用错了 table-layout，当场改掉，再完整跑一遍 C1–C11 自查。

Step 4二轮：反校验，AI 也会偷懒

人工要求它针对显著问题再做一轮深度自检，防止它盲目判定自己生成的没问题。这一轮重新读产物、逐控件出证据表（PASS / FAIL），把一轮漏掉的图标、颜色继承等细节揪出来。

它的边界

Honest limits

机器不替代人

同一个模型既生成又自检，会带着生成时的盲点，"盖章"只能大幅降低、不能根除，人工复核仍是最后一道。

不是万能生成器

文档里没有的组件 / 规则，AI 会停下询问，而不是自由发挥——这是特性，不是 bug。
